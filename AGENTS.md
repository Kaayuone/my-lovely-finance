# my-lovely-finance — правила проекта

Мобильное приложение (Capacitor + Android) для учёта личных финансов: траты по карте записываются
сами из уведомлений банка, наличные — вручную. Веб-сборка используется для dev и как runtime
Capacitor. Хранение данных — локальный SQLite. Сети нет — все данные локальны.

**Перед задачей загляни в карту документации [`docs/README.md`](docs/README.md)**: она говорит, какой
документ читать перед правкой схемы БД, захвата уведомлений, вёрстки или Android-конфигурации.
Что строим и что не входит в MVP — [`docs/product/mvp.md`](docs/product/mvp.md); срез проекта —
[`docs/architecture/project-context.md`](docs/architecture/project-context.md).

Проект — младший брат My Lovely Car (`D:\Work\my-lovely-car`, дальше MLC): стек, раскладка и
инструменты взяты оттуда, код переносится копией с первой задачей, которой он нужен
([ADR-0001](docs/adr/0001-stack-and-repository-layout-follow-my-lovely-car.md)). Перед тем как
писать с нуля сервис, компонент или нативный плагин, проверь, нет ли его в MLC: список ещё не
перенесённого — в [`project-context.md`](docs/architecture/project-context.md#что-из-my-lovely-car-ещё-не-перенесено).

## Стек

- **Vue 3** (`<script setup lang="ts">`, Composition API) + **TypeScript**
- **Pinia** — состояние (setup-style сторы)
- **Vue Router** — навигация
- **PrimeVue 4** (тема Aura) + **TailwindCSS v4** + `tailwindcss-primeui`
- **Capacitor 8** + `@capacitor-community/sqlite` (нативно) / `jeep-sqlite` + `sql.js` (веб)
- **@lucide/vue** — иконки

Согласованы как часть стека, но ставятся с первой задачей, которой нужны: `valibot` (валидация
форм), `vue-virtual-scroller` (длинные списки), плагины Capacitor из MLC (`@capacitor/keyboard`,
`@capacitor/haptics`, `@capacitor/local-notifications`, `@capacitor/filesystem`, `@capacitor/share`).
Любая другая зависимость — только по согласованию.

## Платформа

Продукт — мобильное приложение под Android: телефоны и планшеты в книжной ориентации. Веб-сборка
нужна только для dev и как runtime Capacitor; десктопного продукта нет и не планируется. Поэтому
десктопными практиками, у которых на телефоне нет пользователя, осознанно пренебрегаем:

- **Клавиатурной доступности списков не делаем.** Строки списков — `div role="button"` с
  обработчиком тапа, без `tabindex` и без `@keydown` на Enter и пробел. Команды строки, которым не
  нужна форма, открывает долгое нажатие и шторка команд, а не контекстное меню (`useLongPress` и
  `RowActionsSheet` переносятся из MLC с первым таким списком).
- Hover-состояния, горячие клавиши, контекстное меню правой кнопкой и раскладки под альбомную
  ориентацию — вне задач. Книжная закреплена в манифесте, но планшет на Android 16+ этого не
  соблюдает: в альбомной у него колонка контента стоит по центру, и требование к ней одно — ничего
  не ломается.

Что остаётся обязательным, потому что работает на телефоне:

- Доступные имена у иконочных кнопок (`aria-label`) — их читает TalkBack.
- Приёмник фокуса в `Dialog` ([`styles-and-layout.md`](docs/conventions/styles-and-layout.md)) —
  иначе PrimeVue подсвечивает крестик.
- Адаптив по тирам 320 / 360 / 400 / 600 / 720 и аппаратная кнопка «назад».

## Структура репозитория

Корень репозитория — само приложение: `src/`, `android/`, `e2e/`, `public/` и их конфиги
(`package.json`, `vite.config.ts`, `capacitor.config.ts`, `playwright.config.ts`).

- `docs/` — документация, `scripts/` — проверки репозитория (`check:docs`)
- `android/` — нативный проект Capacitor; свои плагины — в `android/app/src/main/java/my/lovely/finance/`
- `e2e/` — Playwright по production-сборке
- `public/` — статические файлы веб-сборки: `assets/sql-wasm.wasm` для веб-SQLite,
  `webview-outdated.html`, `third-party-notices.txt`

## Структура `src/`

- `entities/<name>/` — слой данных по сущности: `*.repository.ts`, `*.mapper.ts`, `*.types.ts`
- `stores/` — Pinia-сторы (`settingsStore.ts`)
- `features/<FeatureDialog>/` — самостоятельные фичи (диалоги/формы), `types.ts`; подкомпоненты
  в `components/` — если их 3 и больше, иначе рядом с диалогом
- `pages/<name>/` — страницы-роуты, компоненты с префиксом `The*` (`TheInbox.vue`); оболочка —
  `pages/layouts/`
- `components/` — переиспользуемые UI-компоненты (`EmptyState.vue`); группу родственных компонентов
  с общей логикой — в подпапку рядом с их composable
- `database/` — инициализация и доступ к SQLite (`database.ts`, `transaction.ts`, `migrations/`)
- `services/<name>/` — инфраструктурные сервисы: `<name>.service.ts`, `<name>.types.ts`,
  `constants.ts`, `index.ts`; composables рядом (`useXxx.ts`)
- `types/` — общие типы: union-типы предметной области
- `constants/` — глобальные константы приложения (`APP_VERSION`); один файл на предметную область
- `router/`, `assets/`

Каталоги из списка, которых ещё нет (`entities/`, `features/`, `types/`, `utils/`), заводятся с
первым модулем.

## Соглашения

- Импорты через алиас `@/` (= `src/`), напр. `import { useSettingsStore } from '@/stores/settingsStore'`.
- Язык UI — **русский**. Комментарии в коде и сообщения об ошибках в консоль/логи — только на
  **английском**.
- Сборка: `npm run dev`, `npm run build`, `npm run lint`, `npm run format` — из корня репозитория.
- Перед push: `npm run lint:ci`, `npm run format:check`, `npm run type-check`, `npm test` — те же
  проверки, что и в CI.
- Версия приложения живёт только в `package.json`. `android/app/build.gradle` читает её оттуда:
  `versionName` — строка как есть, `versionCode` — `major * 10000 + minor * 100 + patch`.
  Руками в Gradle версию не правим.
- Деньги — данные пользователя: ошибка в сумме, валюте или знаке хуже падения. Правило хранения
  сумм фиксирует ADR модели данных; до него сумм в коде нет.

## Core workflow

- Делай минимальное изменение, решающее задачу.
- Не выходи за пределы модуля, которому принадлежит проблема.
- Не рефактори, не переименовывай, не перемещай файлы и не меняй архитектуру, если это не требуется
  задачей.
- Переиспользуй ближайшие паттерны вместо новых абстракций.
- Если задача может затронуть более 5 файлов, общие контракты, схему БД, конфиг сборки или
  поведение всего приложения — сначала предложи короткий план перед правками.

## Определение готового результата

Задача закончена, когда выполнено всё перечисленное, а не когда код работает:

- прогнаны проверки уровня задачи и приложен их результат — профили в
  [`docs/testing/profiles.md`](docs/testing/profiles.md);
- обновлена документация, если изменение затронуло схему БД или миграцию, инвариант, публичное
  поведение, команду, скрипт, джобу CI или правило разработки — что именно править, говорит
  [`docs/workflows/docs-update.md`](docs/workflows/docs-update.md);
- выбор между вариантами с ощутимой ценой зафиксирован как ADR в [`docs/adr/`](docs/adr/), а не
  растворён в коде;
- пункт `TODO.md` перенесён по правилам ниже;
- заметное пользователю изменение записано в [`CHANGELOG.md`](CHANGELOG.md), раздел «Не выпущено»,
  по правилам из его шапки;
- названо то, что проверить не удалось: устройство, сеть, секреты, внешние сервисы.

Документация — часть результата, а не отдельная задача «на потом». `npm run check:docs` проверяет
механику (ссылки, статус-блоки, дрейф версий); смысловую актуальность подтверждает автор изменения.

## Code rules

- Сохраняй строгие настройки TypeScript.
- Предпочитай точные существующие типы/контракты; избегай `any`, если это не уже принятый локальный
  паттерн границы.
- Используй `import type` для type-only импортов.
- Переменная в `catch` — `error`. `caught` — только когда `error` в этой области видимости уже
  занято, например реактивным состоянием ошибки.
- Константы — в `constants.ts` (локальный или `src/constants/`), не в `utils.ts`; в `<script setup>`
  допустимы, пока компонент небольшой (~150–200 строк).
- Не редактируй сгенерированные, build-, dependency-, cache- или output-папки.
- Не добавляй зависимости без явного согласования.
- Лицензии npm-пакетов бандла перечисляет сборка (`build.license` → `licenses.json`). Зависимость,
  которой нет в графе модулей бандла — готовый бандл со своими зависимостями внутри, только CSS,
  шрифт, нативная библиотека Android, — дописывается в `public/third-party-notices.txt` с текстом
  лицензии.
- Не коммить и не выводи секреты.

### Приведение типов

- Приведение через `as` — только в крайних случаях, когда TS объективно не может вывести тип сам.
  Везде, где тип выводится автоматически или его можно задать дженериком/аннотацией параметра, —
  обходимся без `as`.
- Типичный оправданный случай: нетипизированный результат внешнего API (`result.values as T[]`
  в `database.ts`).
- В `<script>` это проверяет `@typescript-eslint/consistent-type-assertions`
  (`assertionStyle: never`): каждое приведение в рантайм-коде требует `// eslint-disable-next-line`
  со строкой причины над ним. В тестах правило выключено, выражения в `<template>` оно не видит.
- Не используем `as` для «затыкания» ошибок типов и `as any` — вместо этого правим сами типы.

### Утилиты, константы и типы: локальные vs глобальные

**Утилиты**

- Перед написанием новой утилиты проверяй существующие:
  1. **Глобальные** `src/utils/` — если подходящая функция уже есть, используй её.
  2. **Локальные** `utils.ts` в соседних фичах и страницах — если утилита найдена там и нужна
     в ≥2 модулях, вынеси в `src/utils/` и используй оттуда; не копируй хелперы между фичами и
     страницами.
- Локальный `utils.ts` рядом с компонентом(ами) — если утилиты используются только внутри одной
  директории и не содержат бизнес-логики (форматирование, лейблы, мелкие хелперы).
- Глобальные `src/utils/` — когда утилита применяется в разных частях приложения.

**Константы**

- Перед объявлением новой константы проверяй существующие: глобальные `src/constants/` (один файл на
  предметную область), затем локальные `constants.ts` в фиче или странице.
- **Не объявляй константы в `utils.ts`, репозиториях, мапперах и пр.** — только в `constants.ts`
  (локальном или глобальном), по той же логике, что типы живут в `types.ts`, а функции — в `utils.ts`.
- Если локальная константа нужна в ≥2 несвязанных модулях — вынеси в `src/constants/`.
- Именование — `UPPER_SNAKE_CASE`; значения без побочных эффектов (без `new Date()` и т.п.
  в глобальных константах — для таких случаев используй функцию или локальный `constants.ts`).
- Простые/небольшие компоненты держат константы прямо в `<script setup>`; локальный `constants.ts` —
  когда файл компонента разросся (~150–200 строк) или константы нужны в ≥2 файлах той же директории.

**Типы**

- Простые/небольшие компоненты держат свои типы прямо в `<script setup>`.
- Локальный `types.ts` рядом — если тип используется компонентом(ами) внутри одной директории
  **и** файл компонента разросся (ориентир ~150–200 строк).
- Глобальные `src/types/` — только для по-настоящему общих типов (union'ы предметной области).
- Сам факт, что тип импортируется в другом модуле, **не** повод поднимать его в глобальные: тип
  фичи остаётся рядом со своим источником и импортируется оттуда.

## Guard clauses

Если `if` содержит только `return` (ранний выход / guard clause), пиши блок в одну строку:

```typescript
// ✅
if (!form.title.trim()) return false;
if (!selectedAccount.value) return;

// ❌
if (!form.title.trim()) {
  return false;
}
```

Не применяй к блокам с несколькими операторами или когда условие/тело слишком длинные для чтения
в одну строку.

## Правила по scope

Правила кода отдельных слоёв лежат в [`docs/conventions/`](docs/conventions/). Перед правкой прочитай
документ своего scope; задача, которая трогает несколько слоёв, читает каждый из них.

| Что правишь | Что прочитать до правки |
| --- | --- |
| `src/entities/`, `src/database/`: репозиторий, маппер, SQL, транзакция, миграция | [`entities-and-sqlite.md`](docs/conventions/entities-and-sqlite.md) |
| `src/stores/`: стор, его `load*` и мутации | [`stores.md`](docs/conventions/stores.md) |
| `.vue`-файл: порядок в `<script setup>`, импорты, атрибуты в шаблоне, имена компонентов | [`vue-components.md`](docs/conventions/vue-components.md) |
| Вёрстка: PrimeVue и `:pt`, цвета, фокус в `Dialog`, тиры ширины, колонка планшета | [`styles-and-layout.md`](docs/conventions/styles-and-layout.md) |
| Прокручиваемый список на `DynamicScroller` | [`virtual-scroller.md`](docs/conventions/virtual-scroller.md) |
| Форма: правила полей, показ ошибок | [`form-validation.md`](docs/conventions/form-validation.md) |
| Unit- и E2E-тесты | [`tests.md`](docs/conventions/tests.md) |

Три правила легко нарушить, не заходя в их scope, — поэтому они повторены здесь:

- SQL — только в репозиториях `src/entities/`; компоненты получают данные только через сторы.
- Каждая запись в БД — через `runInTransaction`, внутри — `executeSql(..., false)`
  ([ADR-0002](docs/adr/0002-schema-built-by-migrations-only-every-write-through-the-transaction-queue.md)).
- Цвета — только ролями (`bg-app`, `bg-card`, `text-muted-color` и т.п.), не числовой шкалой
  `surface-*`.
