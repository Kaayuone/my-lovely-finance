# ADR-0002. Схема SQLite строится только миграциями, каждая запись идёт через очередь транзакций

- **Статус:** принято
- **Дата:** 10 ноября 2026
- **Этап:** каркас, версия 0.1.0
- **Связанные документы:** [`data-layer.md`](../architecture/data-layer.md),
  [`workflows/migrations.md`](../workflows/migrations.md),
  [ADR-0001](0001-stack-and-repository-layout-follow-my-lovely-car.md)

## Контекст

Слой SQLite взят из My Lovely Car (ADR-0001). Там схема описана дважды: полной формой
(`CREATE_SCHEMA`, индексы, встроенные строки) для новой установки и цепочкой миграций для старых баз.
Так сложилось, потому что раннер миграций появился позже первых установок. Цена — тест
эквивалентности со снимками старых схем и класс ошибок «новая установка и обновлённая база
расходятся». Здесь база начинается с нуля, и эту двойственность можно не заводить.

Второе — транзакции. Оба адаптера SQLite читают флаг `transaction` у `execute`/`run` как «оберни
этот оператор в свою транзакцию». Внутри открытой транзакции веб (jeep-sqlite) коммитит её после
первого же оператора, а Android падает с «Already in transaction» и бросает открытую. Соединение
держит одну транзакцию, а действия пользователя пересекаются: переключение настройки во время
сохранения, импорт черновиков при возврате в приложение. В My Lovely Car это решено очередью
транзакций и проверено на устройствах.

## Рассмотренные варианты

**Как в My Lovely Car: полная схема плюс миграции.** Новая установка быстрее, но два источника
правды и тест эквивалентности на каждый шаг. Отвергнуто.

**Только миграции.** Новая установка проходит все шаги с версии 0, существующая база — недостающие.
Один источник правды; цена — время первого запуска растёт с числом шагов (миллисекунды на SQLite).
Принято.

**Query builder или ORM (Kysely, Drizzle) поверх адаптера Capacitor.** Новая зависимость,
адаптеры к `@capacitor-community/sqlite` незрелы, а транзакционная семантика адаптеров всё равно
остаётся на нас. Отвергнуто.

## Решение

- Единственная таблица вне миграций — `schema_version`; её создаёт раннер. Таблицы, индексы и
  встроенные строки — только шагами `MIGRATIONS` (`src/database/migrations/definitions.ts`).
- Шаг миграции — одна транзакция вместе с новой версией. Шаги только дописываются: выпущенный шаг не
  правится, ошибку исправляет следующий. Это держит снимок SQL
  (`src/database/migrations/__tests__/__snapshots__/migrations.sql`).
- Каждая запись приложения — через `runInTransaction`, одиночная тоже; внутри — `executeSql(sql,
  values, false)`. Пока транзакция открыта, `executeSql` без `false` бросает ошибку.
- Транзакции, пришедшие во время другой, ждут её конца и идут по порядку прихода. Вложенный
  `runInTransaction` ждёт сам себя — репозиторий, которому нужна чужая запись внутри своей
  транзакции, зовёт её `*InTransaction`-вариант.
- Внешние ключи проверяются чтением `PRAGMA foreign_keys` на каждом новом соединении; соединение
  без них — ошибка старта, а не тихая порча данных.

## Последствия

- Встроенные строки (например, стандартные категории) — шаг миграции: изменение встроенного
  каталога — новый шаг, а не правка старого.
- Пересборка таблицы (ограничения `ALTER TABLE` в SQLite) — обычный шаг: новая таблица, копия
  данных, удаление, переименование.
- Сжать старые шаги в один «базовый» для новых установок можно будет только новым ADR, с тестом, что
  результат совпадает с цепочкой.
- Если решение отменят и вернут полную схему, понадобится тест эквивалентности, как в My Lovely Car.
