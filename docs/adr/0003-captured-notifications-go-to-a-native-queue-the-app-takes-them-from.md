# ADR-0003. Пойманные уведомления пишутся в свою нативную очередь, приложение забирает их оттуда

- **Статус:** принято
- **Дата:** 10 ноября 2026
- **Этап:** этап 1, версия «для себя»
- **Связанные документы:** [`notification-capture.md`](../architecture/notification-capture.md),
  [`data-layer.md`](../architecture/data-layer.md),
  [`product/bank-notifications.md`](../product/bank-notifications.md),
  [ADR-0002](0002-schema-built-by-migrations-only-every-write-through-the-transaction-queue.md)

## Контекст

Слушатель уведомлений — служба Android (`NotificationListenerService`). Система поднимает ради неё
процесс приложения без экрана и без WebView, то есть без всего TS-кода: миграций, очереди транзакций
и разборщика. Пойманный пуш может записать только Java, и до появления WebView ему нужно место.

Основная база принадлежит `@capacitor-community/sqlite`. Плагин работает через свою копию SQLite —
SQLCipher (`net.zetetic:sqlcipher-android`), а служба живёт в том же процессе. Две копии SQLite на
одном файле в одном процессе портят базу: блокировки одной копии снимаются, когда другая закрывает
файл (sqlite.org, «How To Corrupt An SQLite Database File», §2.2.1).

## Рассмотренные варианты

**Своя нативная очередь.** Служба пишет сырую запись в отдельный файл `capture.db` встроенным
SQLite Android; приложение при старте, при возврате на экран и по событию плагина забирает новые
записи, разбирает их на TS и одной транзакцией `runInTransaction` пишет черновики в основную базу.
У основной базы остаётся один писатель, схема основной базы не известна Java, сырой текст хранится и
может быть разобран заново. Цена — второе хранилище и код переноса. Принято.

**Служба пишет сразу в основную базу.** Одно хранилище и никакого переноса, но: риск порчи файла
(или явная зависимость от SQLCipher той же версии, что у плагина), имена таблиц и колонок в двух
языках, окно после обновления APK, когда служба пишет в схему, которую ещё не обновили миграции,
запись мимо очереди транзакций посреди открытой транзакции JS, разборщик на Java и путь, который не
проверить ни в вебе, ни в E2E. Нужно было бы исключение из ADR-0002. Отвергнуто.

**Очередь в SharedPreferences или файле JSON.** Дешевле своей базы, но SharedPreferences
переписывает весь файл на каждую запись и сбрасывает его на диск асинхронно — убитый процесс теряет
последний пуш; в файле построчного JSON убийство оставляет оборванную строку; журнал для экрана не
запросить. Отвергнуто.

**JS в фоне** — `@capacitor/background-runner` или WebView без экрана. Runner запускается по
расписанию не чаще раза в 15 минут, событий слушателя не получает и к плагину SQLite доступа не
имеет; WebView без экрана тяжёл, и оболочки производителей убивают такой процесс первым.
Отвергнуто.

## Решение

- Служба пишет только в `capture.db`, свою базу на `SQLiteOpenHelper`; её схема живёт в Java
  (`CaptureDatabase.java`) и меняется только его `onUpgrade`, не миграциями приложения.
- В `capture.db` — белый список приложений, сырые уведомления и события службы. Белый список хранится
  здесь, а не в Preferences: его читает служба, когда WebView нет.
- Запись повторного показа того же уведомления отбрасывается по отпечатку: пакет, ключ уведомления и
  тексты.
- При подключении служба переписывает уведомления выбранных приложений, которые ещё висят в шторке:
  так видно, что пришло, пока она была отвязана.
- Перенос в основную базу — на TS, с подтверждением забранных записей после коммита: запись,
  забранная повторно после убитого процесса, отбрасывается уникальной ссылкой черновика на запись
  очереди. Перенос появляется вместе с черновиками; до него очередь — журнал захвата.

## Последствия

- Два хранилища. `capture.db` не проходит через миграции приложения и не видна его тестам SQLite;
  схему очереди проверяет только устройство.
- Пока приложение не открыто, разобранной суммы нет: уведомление «Записать 12,50 BYN?» прямо из фона
  потребует разборщика на Java или переноса разбора в службу — это новый ADR.
- Сырые тексты уведомлений банков лежат на телефоне 90 дней; системный бэкап берёт `capture.db`
  вместе с основной базой — по тому же открытому вопросу о бэкапе финансовых данных
  ([`TODO.md`](../../TODO.md), «Рассмотреть»).
- Если решение отменят и служба начнёт писать в основную базу, понадобятся: исключение из ADR-0002,
  SQLCipher версии плагина в Gradle и проверка схемы основной базы службой перед каждой записью.
